# Browser and accessibility baseline

The invited studio, all 26 registered Crafts, Notes and Robyn's browser tools are desktop-only. Compact native editors are outside the pilot. The initial entry check requires a viewport of at least 1200 CSS pixels, a fine pointer and hover. It is a presentation check, not proof of GPU/codec support. A temporarily narrowed window preserves an already-open editor and its unsaved state. The detailed browser/accessibility exercises below were recorded on October 25, 2026; [current acceptance](CURRENT-STATUS.md) separately indexes the October 30 fourteen-Craft refresh.

| Environment | Evidence / support claim |
| --- | --- |
| Desktop Chromium | Recorded production Craft/Research acceptance and isolated browser regressions. This is the tested baseline |
| DashCraft read-only reports | Exact private-library computation, slicers, DAX, model/TMDL views, native export and reload passed in desktop Chromium. The final original UI/engine also refreshed and computed the report and DAX oracle in Firefox and Playwright WebKit using local exact-input transport fixtures; this does not certify physical Safari or every M/DAX/visual feature |
| SubCraft browser painting | Current 0.1.8 native writer and brush/layer loop passed in desktop Chromium with an available hardware WebGPU adapter. Its own startup area explains an unavailable adapter; additional engines/GPUs and all bake/export operations are unaccepted |
| User's Chrome Home profile | Intended ordinary Chrome profile; historical startup comparison remains a scoped case. Do not interpret it as failure of every current editor |
| Edge desktop | Intended Chromium-family browser; separate branded-browser acceptance not completed |
| Firefox 157 / Playwright WebKit 27.2 on Windows | PhotoCraft, SoundCraft and FilmCraft 0.1.4 opened real saved projects in each engine. This is startup evidence, not full native editing/playback acceptance or a Safari claim |
| Safari / additional physical GPUs | Unverified. No browser-engine emulation is a physical Safari or GPU acceptance result |
| Chromium mobile emulation | Public homepage/entry presentation recorded at 390 × 844; native editor not mounted on unsupported first entry |
| Physical phones/tablets | Public-site acceptance pending. No native compact-editor claim |

The deployed release has a post-build public gate (`npm run test:public`) covering the homepage, Support and Privacy at 1440 × 1000 and 390 × 844. Chromium, Firefox and WebKit run axe WCAG A/AA checks, page-error and overflow checks. The Windows WebKit port excludes ordinary links in its default Tab navigation; a plain HTML anchor reproduces this outside Robyn, so four Support/Privacy keyboard cases are explicitly unverified, not counted as passes. Chromium/Firefox keyboard focus passes. Hosted Linux CI passes all 18 combinations, including keyboard focus, without platform exclusions. This does not certify Safari, physical devices, thirteen native applications or a complete screen-reader workflow. A maintained real-component regression verifies that compact first entry mounts no editor, then opening on desktop, narrowing and widening preserves the exact iframe and unsaved input. The notice traps focus and refuses Escape while the studio is unsupported. The October 25 production rollout also passed actual Chromium desktop/mobile homepage visual review and the compact studio entry notice.

The real Media panel now has maintained tests in Chromium 156, Firefox 157 and WebKit 27.2. WCAG A/AA axe checks, dialog keyboard entry/Escape/focus return, forced colors, reduced motion, minimum desktop width, and reflow at a halved CSS viewport pass. The last check approximates the layout effect of 200% browser zoom; it is not an OS magnifier or manual browser-zoom certification. No horizontal or vertical modal-bound overflow was found, and keyboard focus scrolls its long form to the relevant control. A lost response, panel remount and retry with zero allowance retain the exact request and the same embedded unsaved editor fixture. Storage failure prevents a new paid submission.

The actual pinned PhotoCraft, SoundCraft and FilmCraft editors also imported the three previously purchased image/speech/video outputs in Chromium, saved native packages and reopened them with exact source bytes and dependency references. Those checks used an isolated bridge; they do not claim production writes or another employee turn. Cross-engine startup is recorded separately. An unrestricted test run while nine native WASM sessions were open exhausted local memory; the sessions were closed and the complete suite passed with a four-process limit. Do not classify that resource-overload run as an editor compatibility result.

Native accessibility remains incomplete. Inspection of PhotoCraft 0.1.4 found an unnamed native text-entry input, and its canvas tools are not exposed as individually named controls in the browser accessibility tree. The Studio asset picker has named search/close/place controls and correct focus return, but a passing DOM-only scan cannot certify the canvas. A future immutable runtime release must address the text-entry name and native semantic/focus support, followed by actual keyboard-only and screen-reader acceptance; do not hide controls solely to silence axe.

Before expanding the baseline, record browser/OS/version, GPU and available graphics/media features, then test actual browser zoom/OS magnification, physical high contrast, screen-reader navigation, and native Open/Save/Save As/Copy across every proposed engine. Also verify playback/seek after URL expiry and interrupted-network recovery. Preserve exact output revisions and keep paid acceptance separately bounded. Physical-phone public-site checks, all thirteen native applications across additional engines, and hardware GPU comparisons remain open.

The public Support page states these limitations. Document options → Browser & accessibility help opens it in a separate tab, retaining the current editor. If an editor cannot initialize, saved native files remain downloadable through File details. Do not tear down an already-open editor merely because a capability probe or window size changes.

The WebKit keyboard preference is described in [Apple’s tabFocusesLinks documentation](https://developer.apple.com/documentation/webkit/wkpreferences/tabfocuseslinks) and [the Playwright maintainer explanation](https://github.com/microsoft/playwright/issues/5609#issuecomment-832684772). The Windows control probe also showed that explicit tabindex links focus while ordinary links do not; no product DOM changes are used to make those tests pass.
